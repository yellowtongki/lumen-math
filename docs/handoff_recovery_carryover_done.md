## 문제 ① 이월 — 처리 완료

요청대로 **기존 45일·완료 필터는 그대로 두고 이월 경로만 추가**했습니다.

| 추가한 것 | 내용 |
|---|---|
| `rcLastDoneEntry(k)` | `RC.state.calls`를 직접 훑어 그 학생의 **직전 완료 건 1개**만 찾음 (요청 1번대로 `rcLedgerData()`는 부르지 않음 — 호출 얽힘 방지) |
| `rcCarryUnits(k)` | 그 완료 건에 `rcHealOf()`를 걸어 `st==='still'`인 단원만 뽑음 (요청 2번) |
| `rcRows()` | `carryHits` 배열을 **`unitHits`와 분리**해 담음 (요청 3번) — `match`/`rx`의 🔴/🟡 판정 로직은 손대지 않았으므로 처방 판정이 흐려지지 않음 |
| `rcRows()` 조기 return | `if(!testHit&&!unitHits.length&&!carryHits.length) return;` 로 수정 (요청 4번) |
| 이미 잡힌 단원 중복 제거 | `rcNrm` 양방향 부분일치로 `unitHits`와 겹치면 이월에 넣지 않음 |

### 표시 (요청 5번)

- **예상 명단 카드** — 보라 점선 칩 `🔁 이월 「단원명」 55%` (🔥 1순위 배지와 별개 자리)
- **처방** — 이월 줄을 `rx` **맨 앞**에 넣음 (지난주에 못 메운 것이 이번 주 1순위)
- **리커버리 학습지 인쇄(`rcPrint`)** — ③번 항목으로 포함, 부제에 `당시 40% → 현재 55%`

### 무한 이월 방지 (요청 「주의할 점」)

**직전 완료 1회분만** 봅니다. 다음 회차에 또 보충하면 그 회차의 🔁가 새 기준이 됩니다.
추가로 `rcSnapOf()`가 **이월 단원도 스냅샷에 넣도록** 고쳤습니다 — 안 그러면 이월된 단원이
다음 회차 스냅샷에서 빠져 🔁 추적이 한 번에 끊깁니다.

성능은 별도 캐시를 두지 않았습니다. `rcHealOf`는 스냅샷 단원(최대 5개) × 교재 수만 도는데
재원생 26명 기준 체감 지연이 없었습니다. 학생이 크게 늘면 그때 캐시를 넣는 것이 좋겠습니다.

## 문제 ② CSV — 처리 완료

`rcLedgerCsv()`에 **`메워짐수`, `남음수`** 두 열을 추가했습니다.
`rcHealOf(c.k, c.e)`의 `healed`/`still`을 그대로 넣고, 판정 불가(`null`)면 빈칸입니다.

## 검증 (요청한 3가지 전부 통과)

실제 Chromium에서 v18-66을 띄우고 픽스처로 확인 — **8/8 통과, 페이지 오류 없음**.

| 케이스 | 기대 | 결과 |
|---|---|---|
| ① 최근 채점 중인 교재 (5일 전) | 기존대로 명단에 오름 · 이월 표시 없음 | ✅ |
| ② 45일 지난 교재 (보충 60일 전 → 채점 50일 전) | 명단에 오르고 🔁 이월 | ✅ |
| ② 완료 처리한 교재 | 명단에 오르고 🔁 이월 | ✅ |
| ③ 60% 넘겨 메워진 단원 | 명단에 **안 오름** | ✅ |
| 이월 처방이 맨 앞줄 | | ✅ |
| 화면에 🔁 이월 칩 | | ✅ |
| CSV 열 추가 · 값 채워짐 | | ✅ |

### 검증 중 확인한 것 — 원본 문서 재현표의 조건 보완

원본 문서의 재현표에 「최근 채점 50일 전 → 장부 🔁 아직 남음」이 있는데,
**보충 완료일보다 교재 채점이 나중이어야** 🔁가 됩니다. 보충 이후 그 교재를 아예
안 풀었으면 장부는 🔁가 아니라 **⏳ 확인 중(`nodata`)** 이고, 이때는 이월도 되지 않습니다
(메워졌는지 안 메워졌는지 아직 모르는 상태이므로 이 동작이 맞습니다).
즉 이월이 걸리는 건 **「보충 후에 풀긴 했는데 여전히 기준 미만 + 그 교재가 45일 넘게 묵었거나
완료 처리됨」** 인 경우입니다. 블로그 문장(「메워졌다는 데이터가 나올 때까지 관리가 이어집니다」)은
이제 코드로 뒷받침됩니다.
