## 왜 이걸 발견했나

블로그 글에 리커버리 사후 추적을 이렇게 썼습니다.

> 🔁 **아직 남음** — 여전히 기준 아래입니다. **다음 리커버리에 다시 부릅니다.**
> (…) **메워졌다는 데이터가 나올 때까지** 관리가 이어집니다.

이 문장이 코드로 뒷받침되는지 확인하다가, **뒷받침되지 않는 경우 두 가지**를

## 문제 ① (본 건) — 장부엔 🔁 남았는데 예상 명단에는 안 오름

### 원인

같은 단원을 두 함수가 **다른 필터로** 보고 있습니다.

| | 함수 | 위치 | 교재 필터 |
|---|---|---|---|
| 장부 메워짐 판정 | `rcHealOf()` | 9327~9351행 | **없음** — 모든 교재를 봄 |
| 예상 명단 자동 선발 | `rcRows()` ② 단원 기준 | 9476~9486행 | **있음** — 아래 2줄 |

`rcRows()` 9479~9480행:

```js
Object.keys(books).forEach(function(bid){
  var d=books[bid]; if(!d||!d.lastDate||bpAgo(d.lastDate)>45) return;  // ← 45일 지난 교재 제외
  if(bpIsDone(sid,bid,d)) return;                                     // ← 완료 처리한 교재 제외
  (d.chapters||[]).forEach(function(c){
    if(c.total>=5&&Math.round(c.correct/c.total*100)<RC.cfg.minUnit){
      unitHits.push({ bid:bid, book:..., n:c.n, rate:..., minP:c.minP, maxP:c.maxP });
    }
  });
});
```

그래서 아이가 그 교재를 덮고 다른 교재로 넘어가 45일이 지나거나, 교재를
「완료 처리」해 두면 → **정답률이 여전히 55%인 단원이 명단에서 조용히 사라집니다.**
장부에는 🔁로 계속 남아 있어서 화면 간 상태가 어긋납니다.

### 재현 확인 (이미 검증함)

판정부만 떼어내 돌린 결과입니다. 55% 단원, 조건만 다르게:

| 상황 | 장부 판정 | 명단 재선발 |
|---|---|---|
| 최근 채점 5일 전 | 🔁 아직 남음 | ○ 다시 오름 |
| 최근 채점 50일 전 | 🔁 아직 남음 | ✕ **안 오름** |
| 교재 완료 처리해 둠 | 🔁 아직 남음 | ✕ **안 오름** |

### 권장 수정 방향

`rcRows()`에 **이월(carry-over) 경로를 추가**합니다. 기존 45일·완료 필터는
그대로 두고(정상 동작임 — 옛 교재가 계속 명단을 더럽히면 안 됨), **직전 완료
리커버리에서 🔁로 남은 단원만 예외로 통과**시키는 방식입니다.

구현 시 참고할 것:

1. **직전 완료 건 찾기** — `rcLedgerData()`가 이미 학생별 `lastDoneE`(가장 최근
   완료 기록)를 계산합니다(9971행). 다만 `rcRows()`에서 `rcLedgerData()`를 부르면
   서로 호출이 얽힐 수 있으니, `RC.state.calls`를 직접 훑어 해당 학생의 최근 완료
   `e`를 찾는 **작은 헬퍼**를 새로 만드는 편이 안전합니다.
2. **🔁 판정 재사용** — `rcHealOf(k, e)`를 그대로 호출하면
   `{healed, still, nodata, items:[{n, then, now, st}]}`가 나옵니다.
   `items` 중 `st==='still'`인 것만 이월 대상입니다.
3. **기존 `unitHits`와 구분** — 이월분은 `carry:true` 같은 표시를 달아 별도로
   넣어 주세요. 이유:
   - `match`/`rx`(처방) 로직이 `unitHits`를 기준으로 🔴진짜구멍/🟡실전약함을
     가르기 때문에(9498~9509행), 이월분이 섞이면 판정이 흐려질 수 있습니다.
   - UI에서 「🔁 이월 — 지난 보충에서 안 메워짐」처럼 따로 보여주는 게
     원장님이 상황을 알아보기 쉽습니다.
4. **조기 return 확인** — 9487행 `if(!testHit&&!unitHits.length) return;`
   이월분만 있는 학생도 명단에 올라야 하므로 이 조건도 함께 고쳐야 합니다.
5. **표시** — 예상 명단 카드(9840행대)에 이월 뱃지 추가. 기존 🔥 1순위 표시와
   충돌하지 않게. 이월 단원은 학습지 인쇄(`rcPrint`, 9533행대)에도 들어가는 게
   자연스럽습니다.

### 주의할 점

- **무한 이월 방지** — 이월된 단원이 영원히 명단에 남으면 안 됩니다.
  이월은 **직전 완료 건 기준 1회분만** 보는 게 안전합니다(그다음 주에 또 보충하면
  그 회차의 🔁가 새 기준이 됨).
- `rcHealOf`는 학생마다 모든 교재를 훑으므로, 명단 렌더링마다 전원에 대해
  호출하면 느려질 수 있습니다. 학생 수가 많으면 결과를 한 번만 계산해
  재사용하도록 해 주세요.
- **기존 동작을 바꾸지 말 것** — 45일·완료 필터 자체는 유지. 이월만 추가.

## 문제 ② (작음) — CSV 내보내기에 메워짐 판정이 빠짐

`rcLedgerCsv()` 10063~10073행. 현재 열 구성:

```
주(토요일) · 이름 · 반 · 상태 · 완료일 · 주간점수 · 진짜구멍수 · 처방유형수
```

화면에는 보이는 **메워짐/남음 판정이 파일에는 없습니다.** 열 두 개
(`메워짐수`, `남음수`) 추가하면 됩니다. `rcHealOf(c.k, c.e)`의
`healed`/`still` 값을 그대로 넣으면 되고, 판정 불가(`null`)면 빈칸으로.

## 문제 ③ (신규, 2026-08-17 추가) — 커트라인이 초등/중고등 구분 없이 단일값

### 발견 경위

원장님이 실제 학부모 안내문 원문을 주셨습니다.

> 수목 주간테스트 시행하여서 **초등부는 70점 중고등부는 80점** 커트라인과
> 단원별 정답율 미흡시, **재시험**과 리커버리학습지로 부족한 부분을 채우는
> 리커버리 수업을 진행합니다. **토요일**에 진행되며, **네이버예약**으로
> 리커버리대상 학생들에게 개별안내 드리고 있습니다.

### 코드와 대조한 결과

`RC.cfg`(9280행)는 다음과 같이 **학년 구분이 없는 단일 값**입니다.

```js
var RC={..., cfg:{minScore:80, minUnit:60, weeks:3, slots:[...], range:null}, ...};
```

`rcRows()`(9470행)도 전 학년 학생에게 같은 `RC.cfg.minScore`를 적용합니다.

```js
if(me&&me.score<RC.cfg.minScore){ ... }   // 초등/중고등 구분 없음
```

즉 원장님이 화면에서 커트라인을 80점으로 맞춰두면 **초등부 학생은 실제
기준(70점)보다 엄격하게** 적용되고, 70점으로 맞춰두면 **중고등부가 실제
기준(80점)보다 느슨하게** 적용됩니다. 지금은 한쪽을 희생해야 하는 상태입니다.
(단원별 정답률 기준 `minUnit`은 학년 구분 언급이 없어 공통 60%로 보이며,
이건 문제가 아닐 수 있습니다 — 확인 필요.)

### 권장 수정 방향

1. `RC.cfg`에 학년군별 값 추가: 예) `minScoreElem`(초등부), `minScoreSec`
   (중고등부) — 기존 `minScore`는 하위호환용으로 남기거나 마이그레이션.
2. `rcRows()`의 점수 비교 시 `st`(학생)의 학년 정보로 초등/중고등을
   판별해 해당 커트라인 적용. 학년 판별은 기존에 쓰는 헬퍼가 있는지 먼저
   확인할 것 (`cpIsElem()` 등 — 48554행 근처에 초등부 판별 로직이 이미
   있습니다. 진학 나침반 기능에서 씀. **재사용 가능할 가능성 높음**).
3. `rcEditCfg()`(9301행)의 "기준 점수 수정" UI도 초등/중고등 두 값을
   따로 입력받도록 조정.
4. 기존 저장된 `rc_config`(Supabase `lumen_store`)와의 호환 — 기존 단일
   `minScore`를 중고등부 기본값으로 취급하고 초등부는 새 필드가 없으면
   70을 기본값으로 채우는 마이그레이션이 안전합니다.

### 참고 — 앱에 없는 개념 (수정 불필요, 참고만)

- **재시험**: 코드에 해당 개념이 없습니다. 실제로는 토요일 리커버리 시간에
  선생님이 구두/지필로 진행하는 것으로 보이며, 앱이 추적할 필요가 있는지는
  원장님 확인 필요.
- **네이버예약**: 학생 개별 안내는 학원앱의 `rcOpenSms`(문자 초안 기능)가
  아니라 네이버예약으로 이뤄지고 있습니다. `rcOpenSms` 자체를 없앨 필요는
  없지만, 실제 안 쓰는 기능이라는 걸 참고해 두시면 좋습니다.

## 검증 방법

수정 후 아래 3가지가 다 맞아야 합니다.

1. **정상 케이스 유지** — 교재를 계속 풀고 있는 학생: 55% 단원이 예상 명단에
   그대로 오름 (기존과 동일, 이월 표시 없음)
2. **이월 케이스** — 45일 넘게 안 푼 교재 / 완료 처리한 교재에 🔁 남은 단원이
   있는 학생: 명단에 오르고 「🔁 이월」로 표시됨
3. **메워진 케이스는 안 오름** — 60% 넘겨 ✅ 메워짐이 된 단원은 이월되지 않음

로컬에서 실데이터 없이 확인하려면 `rcHealOf`/`rcRows`의 단원 필터 부분만
떼어내 노드로 돌리는 방식이 빠릅니다 (블로그 세션에서 그렇게 검증했습니다).
브라우저 검증은 `/verify` 스킬 사용.

## 참고 — 이번에 확인한 리커버리 판정 규칙 (정확함)

문서화가 안 돼 있어 같이 남깁니다.

| 판정 | 조건 |
|---|---|
| ✅ 메워짐 | 보충 이후 그 단원 **새 채점 기록 있고**, 정답률 ≥ `RC.cfg.minUnit`(기본 60) |
| 🔁 아직 남음 | 새 채점 기록 있는데 정답률 < 기준 |
| ⏳ 확인 중 | ① 보충 후 그 교재 안 풀었음(`d.lastDate <= e.done`) ② 매칭 단원 없음 ③ 그 단원 문항 `total < 5` (표본 부족) |
| 판정 불가(`null`) | 호출 기록에 `snap.units`가 없음 (v17-28 이전 옛 기록) |

- 단원명 매칭은 `rcNrm()`(9446행)으로 숫자·점·괄호·공백을 떼고 **양방향 부분일치**.
  「3. 이차방정식의 활용」 ↔ 「이차방정식」도 매칭됨(확인함).
- 같은 단원이 여러 교재에 있으면 **가장 높은 정답률**을 취함(9341행) — 관대한 판정.
- 기준점(당시 정답률)은 호출을 켜는 순간 `rcSnapOf()`(9311행)가
  `snap.units:[{n, rate}]`로 최대 5개까지 저장.
